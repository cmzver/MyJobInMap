# План: кабинет УК, уведомления заявителю, склад, деньги

Решение пользователя 2026-11-03: после закрытия плана актов и ТО
(`docs/field-service-plan.md`) берём кабинет УК, уведомления заявителю, склад
материалов и технический долг. Маршрут дня и расчёт оплаты мастерам — не сейчас.

## 1. Что уже есть (не делаем заново)

- **Идемпотентность записей Android** — `Idempotency-Key` (`services/idempotency.py`)
  на актах, фото, комментариях, статусах, удалённых действиях; материалы — по `operation_id`.
- **Неотправленные действия в Android** — баннер «Не отправлено: N», лист с
  «Повторить» / «Удалить» (`OfflineBanner`, `retryFailedAction`, `discardFailedAction`).
- **Портал**: общий refresh на параллельные 401 (`api/client.ts`).
- **Деплой**: API и worker из собранного образа, `./server` не монтируется; миграции —
  отдельный one-shot сервис; пароль БД в логах маскируется.
- **Склад (частично)**: справочник `materials`, остатки у исполнителей `material_stocks`,
  журнал `material_movements` (идемпотентный `operation_id`), списание на заявку,
  страница портала «Материалы».
- **Контрагенты** (`counterparties`, `addresses.counterparty_id`) и сводный акт за месяц.
- **Outbox** (`services/outbox_service.py`) — гарантированная доставка после коммита.
- **Публичная ссылка на акт** `/portal/a/<токен>` с подписью — образец для новых
  публичных страниц (только под `/portal/` и `/api/public/`, Caddy не трогаем).

## 2. Порядок

| Шаг | Фаза | Объём |
|---|---|---|
| 1 | Д — деньги в `Numeric` | S |
| 2 | С1–С3 — склад: прайс ↔ склад, общий склад, отчёт | M |
| 3 | К1–К3 — кабинет УК | L |
| 4 | У1–У3 — уведомления заявителю | M |
| 5 | Android: материалы мастера + статус-ссылка (одна версия) | M |

Каждая фаза — своя ветка, слияние в `main` merge-коммитом. Миграции нумеруются
после последней ревизии в `server/alembic/versions/` (параллельная сессия!).
Деплой на прод — после согласия пользователя.

## 3. Фаза Д — деньги

`tasks.payment_amount` и `address_systems.monthly_cost` — `Float`. После фазы 4d
по ним считаются деньги (абонплата в сводном акте, суммы заявок) — переводим в
`Numeric(12, 2)` с округлением при миграции. Контракт API не меняется: в JSON
остаются числа (`float` в схемах), внутри сервера арифметика на `Decimal`.

Не делаем: составные индексы «на глаз» (аудит требует сначала замеров на проде),
разворот зависимости domain → data в Android (рефакторинг без пользы для заказчика).

## 4. Фаза С — склад

**С1. Прайс ↔ склад.** `service_catalog_items.material_id` (nullable) — строка прайса
«материал» связывается с позицией склада. При создании акта по заявке связанные
строки досписываются с остатка исполнителя акта: списывается
`qty в акте − уже списано этим исполнителем на эту заявку`, чтобы ручное списание на
заявку и акт не задваивались. `operation_id = act:<id>:line:<n>`. Нехватка остатка
акт **не блокирует** (акт — документ клиента): остаток уходит в минус и
подсвечивается как недостача. Аннулирование акта возвращает списанное актом.

**С2. Общий склад.** `materials.warehouse_quantity` — остаток на складе организации
(один склад). В журнале — вид операции `kind`: `receipt` (приход на склад),
`issue` (склад → мастер), `return` (мастер → склад), `write_off` (на заявку),
`act` (по акту), `adjust` (инвентаризация). Для операций склада `user_id` пустой.
Минимальный остаток `materials.min_quantity` — подсветка «пора закупать».

**С3. Отчёт.** Обороты за месяц: по мастеру и материалу — на начало, получено,
списано (вручную / по актам), возвращено, на конец, сумма по себестоимости;
выгрузка Excel. На странице «Материалы» — вкладки «Остатки», «Журнал», «Обороты».

**Сделано 2026-11-03** (миграция `20261103_0002`). Сервер: `services/stock_service.py`
(проводки, досписание по акту, обороты), `api/materials.py` (эндпоинты материалов вынесены из
`operations.py`, прежние пути сохранены): `PATCH /materials/{id}`, `GET /materials/balances`,
`POST /materials/operations`, `GET /materials/movements`, `GET /materials/turnover(.xlsx)`.
Портал: «Материалы» — вкладки «Остатки», «Журнал», «Обороты», «Справочник», окно операции;
в прайсе у строки-материала — выбор позиции склада. Попутно: `useUsers` для не-админа брал
`/admin/users` (403) — у диспетчера были пустые списки исполнителей на ТО, карте, дашборде,
складе; теперь не-админ получает активных пользователей из `/api/users`.
Отступления: единицы прайса и склада считаются одинаковыми; у мастера по умолчанию нет
`edit_tasks`, поэтому его основной путь списания — акт (ручное списание на заявку — диспетчер
или группа с этим правом); ручное списание после акта не пересчитывает досписанное актом.

## 5. Фаза К — кабинет УК

Отдельный вход для представителей контрагента (УК/ТСЖ): видят только свои объекты.

**Изоляция.** Отдельная таблица `client_accounts`, а не пользователь с ролью: иначе
кабинет попадает под гейтинг «всё не admin/dispatcher — работник» и десятки
эндпоинтов. Токены кабинета — JWT с `type = "client"` / `"client_refresh"`;
обычная авторизация такие токены уже отвергает (строгая проверка `type`).
Эндпоинты кабинета — только `/api/client/*` со своей зависимостью.

**К1. Сервер.** `client_accounts` (organization_id, counterparty_id, login,
password_hash, full_name, phone, email, is_active, last_login_at, token_version).
`/api/client/auth/login|refresh`, `me`, `objects` (объекты контрагента, системы,
абонплата), `tasks` (список с фильтрами, карточка: статусы, плановая дата,
исполнитель, акты; внутренние комментарии не показываются), `acts` (+ PDF, сводные),
`maintenance` (ближайшие ТО по объектам), `POST tasks` — заявка от УК
(`tasks.client_account_id`, уведомление диспетчерам как о новой заявке).
Управление входами — `/api/counterparties/{id}/accounts` (создать, сбросить пароль,
отключить); право `manage_counterparties` (как у страницы «Контрагенты»).
Включатель кабинета — настройка организации. Rate-limit входа — как у основного.

**К2. Портал.** `/portal/client/login` и раздел `/portal/client/*` со своей
шапкой: «Заявки», «Объекты», «Акты», «ТО», «Новая заявка». В карточке контрагента —
блок «Вход в кабинет».

**К3. Подпись сводного акта в кабинете** — тем же механизмом подписи, что у ссылки
клиенту (4c); подписант — представитель из `client_accounts`.

**Сделано 2026-11-03..05** (миграция `20261103_0003`). Сервер: `models/client.py`,
`services/client_cabinet.py` (вход, токен `type="client"`, видимость), `api/client.py`
(`/api/client/*`), входы — `/api/counterparties/{id}/accounts`. Портал: `/portal/client/*`
(`pages/cabinet/`) со своей сессией (`fieldworker-cabinet` в localStorage) и своим HTTP-клиентом;
карточка «Кабинет клиента» на странице контрагента (пароль генерируется и показывается один раз).
Подпись — тот же `sign_by_link` с `via="cabinet"`. Отступления: включатель кабинета в настройках
организации не делали (вход есть только у тех, кому его выдали); логин глобально уникален;
refresh-токена нет — сессия 12 ч, потом вход заново.

## 6. Фаза У — уведомления заявителю

**У1. Страница статуса заявки** `/portal/t/<токен>` (`tasks.public_token_hash`,
токен выдаётся по запросу из карточки, как у акта): номер, адрес, статус и его
история, плановая дата, акт при выполнении. Без ФИО заявителя и внутренних комментариев.

**У2. Telegram.** На странице статуса — «Получать уведомления в Telegram»: ссылка
`t.me/<бот>?start=<код>`. Существующий бот обрабатывает `/start <код>` и
регистрирует `chat_id` на сервере (сервисный вход бота). Сервер отправляет сообщения
через Bot API из outbox (`kind = "client_message"`): принята, назначена дата,
выполнена (+ ссылка на акт), отменена. Нужны `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_BOT_USERNAME` в окружении API.

**У3. SMS.** Провайдер за интерфейсом (первый — SMS.ru по HTTP), настройки
организации: ключ, какие события. Выключено по умолчанию (платно). SMS на
`customer_phone`: «заявка принята — ссылка на статус», «выполнена».

**Сделано 2026-11-05** (миграция `20261105_0001`). Сервер: `services/applicant_notify.py`,
`api/public_tasks.py` (`GET /api/public/tasks/{token}`, подписка бота
`POST /api/public/tasks/telegram/subscribe|unsubscribe` с заголовком `X-Bot-Secret` =
sha256(TELEGRAM_BOT_TOKEN), `POST /api/tasks/{id}/status-link`), outbox-виды `telegram_send`,
`sms_send`; хуки — создание заявки (и из кабинета), смена статуса, плановая дата. Бот: `/start <код>`,
`/stop`. Портал: `/portal/t/<токен>`, кнопка «Ссылка заявителю» в карточке заявки, блок
«Уведомления заявителю» в настройках организации (ключ SMS.ru только записывается).
Отступления: токен статуса хранится открыто (одна ссылка для SMS, Telegram и диспетчера);
ссылка бессрочная; SMS только при приёме и выполнении; ошибки SMS.ru (ключ, баланс) не
повторяются — только в журнал.

**Для деплоя:** в `server/.env` API добавить `TELEGRAM_BOT_TOKEN` (тот же, что у бота) и
`TELEGRAM_BOT_USERNAME`, желательно `PUBLIC_BASE_URL` (иначе в Telegram/SMS ссылка без адреса не
уходит); пересобрать контейнер бота.

## 7. Android (одна версия)

- «Мои материалы» — остатки мастера, недостача красным.
- В акте строка прайса со складом показывает остаток мастера.
- В карточке заявки — «Ссылка на статус» (поделиться с заявителем).

## 8. Риски

- Двойное списание (вручную на заявку + актом) — правило досписания, тест.
- Утечка данных между контрагентами — каждый запрос кабинета фильтруется по
  `counterparty_id` аккаунта; тесты на чужой объект/заявку/акт → 404.
- Персональные данные на странице статуса — минимум полей, токен в БД только хешем.
- Стоимость SMS — выключено по умолчанию, дедупликация событий.
