# Защита production-сервера — 17 ноября 2026

Сервер: `balalayka.duckdns.org`, hostname `boris`, Ubuntu 24.04 LTS.
Работы выполнены по запросу владельца после проверки журналов.

## Причина

В сохранившихся auth-журналах за 18 октября — 17 ноября обнаружены
246 823 неудачные попытки парольного SSH-входа с 2 032 IP. Все успешные
SSH-входы в этом периоде выполнены двумя существующими ключами владельца.
Cloud-init включал парольную аутентификацию раньше основной настройки
`PasswordAuthentication no`; эффективное значение было `yes`.

## Применённые настройки

- `/etc/ssh/sshd_config.d/00-security-hardening.conf`: обязательная
  аутентификация `publickey`, отключены парольный и keyboard-interactive
  входы; root допускается по ключам. Отключён X11 forwarding.
  `MaxAuthTries 3`, `MaxStartups 10:30:60`, `LoginGraceTime 30`,
  `LogLevel VERBOSE`. Порт 22 и SSH-туннели сохранены.
- Fail2ban установлен и включён при загрузке. `/etc/fail2ban/jail.local`:
  jail `sshd`, systemd backend, aggressive filter, nftables на TCP 22;
  пять ошибок за десять минут, бан на час с увеличением при повторениях
  до семи суток. Исключены только loopback-адреса.
- В Caddyfile до маршрутизации и SPA fallback добавлен ответ 404 для
  `.env*`, `.git`, `.svn`, `.hg`, `.DS_Store` в любом сегменте пути.
  Соседние домены «говорилки» и LiveKit сохранены.
- `/opt/fieldworker/.env`: права изменены с 0644 на 0600.
- Автообновления безопасности уже были включены; это явно закреплено в
  `/etc/apt/apt.conf.d/99-security-hardening`. Автоматическая перезагрузка
  отключена. После обновления индексов APT доступных обновлений из
  security-репозиториев Ubuntu не найдено; это не означает отсутствия
  обновлений из других источников.
- PostgreSQL и API продолжают слушать только 127.0.0.1. Внешняя проверка
  подтвердила отсутствие TCP-доступа к 5432, 8001, 6379, 2375, 2019,
  8080 и 3000 с проверяющего компьютера.

## Проверки и восстановление

Перед SSH-изменением настроен пятиминутный автоматический откат. После
успешных новых подключений обоими ключами и подтверждения, что сервер
предлагает только publickey, таймер отката отменён. `sshd -t` проходит.

Работа nftables action Fail2ban проверена кратковременной блокировкой
тестового адреса 192.0.2.123; правило для TCP 22 проверено, адрес разблокирован.
Тестовый бан учитывается в общем счётчике Fail2ban до его перезапуска.

Caddy проверен через `caddy validate` и применён через reload. Старый
bind mount указывал на удалённый inode; поэтому для reload использован
`/config/security-hardening/Caddyfile` внутри контейнера, а файл на хосте
обновлён для следующего запуска. Подробности — в runbook Prod Deploy.

Проверены девять вариантов секретных путей, включая URL-кодирование,
верхний регистр и путь внутри assets: все вернули 404. Портал, API health,
главная страница «говорилки» и LiveKit вернули 200. SHA-256 HTML портала
совпал до и после reload. Отдельная внешняя HTTPS-проверка портала — 200.

После согласованной перезагрузки сервер проверен 17 ноября в 22:29
Europe/Berlin: работает ядро `6.8.0-149-generic` вместо `6.8.0-134-generic`,
маркер необходимости перезагрузки отсутствует. Все 12 контейнеров
запущены, контейнеры с healthcheck здоровы, ошибок systemd нет.
SSH обоими ключами, Fail2ban и UFW работают после загрузки.

Повторно проверены портал и его JS/CSS-ресурс, API health, «говорилка»
и LiveKit: 200. API `/api/auth/me` без авторизации возвращает 401,
секретные пути — 404. Сервис Pulsar relay активен и принимает TCP 24600.
С внешнего компьютера повторно получены 200 для портала и health,
404 для `/portal/.env`. SHA-256 HTML портала сохранён; после перезапуска
содержимое bind mount Caddyfile совпадает с файлом на хосте.

Бэкап конфигурации и результаты проверок на сервере:
`/var/backups/security-hardening/20261117T212152Z/`, доступ только root.
Содержит исходные SSH/UFW/APT-конфигурации, Caddyfile, runtime-конфигурацию
Caddy, результаты HTTP-проверок и скрипт аварийного SSH-отката.
