# Технический анализ FieldWorker / MyJobInMap

Дата: 25 октября 2026 года. Анализ текущего рабочего дерева, включая существующие незакоммиченные изменения. Прикладной код в рамках анализа не изменялся.

## Статус исправлений на 26 октября 2026 года

Исправлены A01–A10 и A13: безопасная раздача SPA, строгие типы JWT, одноразовая ротация refresh-сессий с отзывом, единая проверка организации, корректный пул и PRAGMA SQLite, fail-fast миграции, tenant-фильтр WebSocket, Room-outbox для плановой даты, безопасный production bootstrap, границы пагинации и честный HTTP 503 health-check. В A12 устранены два главных риска на клиенте: конкурентный запуск сериализован Mutex-ом, а refresh больше не затирает локально изменённые задачи; серверная идемпотентность и отдельная модель конфликтов остаются дальнейшей работой. Добавлены Alembic/Room-миграции и регрессионные тесты.

Вторая итерация закрыла наиболее рискованные части A11, A12 и A14: login/refresh/password hashing и геокодирование создания заявки больше не выполняются в event loop; создание заявки и связанных DB-уведомлений имеет одного владельца транзакции; push-worker повторяет временные ошибки и не создаёт inline-дубликат при неопределённом timeout подтверждения Redis. Android outbox атомарно пишет локальное состояние с действием, различает retryable/permanent/auth ошибки, сохраняет данные при 401, не проглатывает CancellationException и не нарушает порядок действий одной заявки. Production Compose применяет Alembic отдельным one-shot сервисом до API/worker; runtime `create_all` удалён из lifespan. Статусы ниже сохранены как исходные результаты аудита и описание причин изменений.

Остаются системное преобразование остальных sync SQLAlchemy-маршрутов (не только самых дорогих), серверные idempotency keys для защиты от повторной доставки после потери HTTP-ответа, UI управления dead-letter действиями, transactional outbox для гарантированной внешней доставки и архитектурные улучшения из раздела рекомендаций.

## Оценка

Проект имеет подходящую для своего масштаба основу: модульный FastAPI-сервер, React-портал, Android с Room и WorkManager, Telegram-бот. Есть сервисный слой, машина состояний заявок, централизованные проверки доступа, OpenAPI-типы, серверные тесты и CI для SQLite/PostgreSQL. Переписывание проекта или разделение на микросервисы сейчас не требуется.

Главные проблемы находятся на границах: выдача файлов, жизненный цикл авторизации, изоляция транзакций SQLite, применение миграций и сохранность офлайн-изменений. Исправление этих границ даст больший эффект, чем масштабный рефакторинг UI.

P0 — исправить немедленно; P1 — ближайший цикл стабилизации; P2 — следующий технический этап. Уровни отражают последствия при достижении соответствующего сценария, а не утверждение, что инцидент уже произошёл в production.

## Подтверждённые дефекты и предлагаемые правки

### A01 · P0 · Чтение файлов вне каталога портала без авторизации

Код: `server/main.py:400–410`, `portal_spa_fallback`.

Сервер складывает `portal_dist / full_path` и передаёт результат в `FileResponse`, не проверяя, остался ли путь внутри каталога сборки. Запрос с закодированными компонентами перехода в родительский каталог позволяет выйти за пределы `portal/dist`.

Подтверждение: TestClient без заголовка Authorization прочитал специально созданный временный файл вне временного каталога портала; HTTP 200, содержимое совпало. Настоящие секреты и рабочие данные не читались. Доступность такого запроса через конкретный production-прокси отдельно не проверялась.

Последствие: чтение файлов, доступных пользователю серверного процесса; в зависимости от размещения это может включать конфигурацию и секреты.

Правка: вычислять `root.resolve()` и `candidate.resolve()`, запрещать пути вне root через `is_relative_to`; учитывать Windows-разделители, абсолютные пути и симлинки. Статические assets отдавать через `StaticFiles`, SPA fallback возвращает только проверенный файл или `index.html`. Добавить регрессионные HTTP-тесты на закодированные переходы, обратные слеши, абсолютные пути и ссылку наружу. Проверять отказ до отправки тела файла.

### A02 · P1 · Refresh-токен принимается как access-токен

Код: `server/app/services/auth.py:99–133`, `get_current_user`.

После проверки подписи читаются `user_id` и `sub`, но не проверяется `type == "access"`. При этом refresh-токен содержит те же идентификаторы и подписывается тем же ключом.

Подтверждение: `get_current_user(refresh_token)` вернул пользователя; `/api/auth/me` с refresh-токеном как Bearer вернул 200.

Последствие: долгоживущий refresh используется для обычных API-вызовов, обходя установленный срок жизни access-токена. Это не даёт чужую роль само по себе, но нарушает границу между типами токенов.

Правка: общая функция проверки access-токена для HTTP и WebSocket с обязательными типом, сроком действия и идентификаторами. Для неверного типа — 401. Проверку разных видов JWT следует делать взаимоисключающей, как требует [RFC 8725 §3.12](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.12).

### A03 · P1 · Объявленная ротация refresh фактически не реализована

Код: `server/app/api/auth/session.py:110–166`, `server/app/services/auth.py:55–75`, `server/app/api/auth/account.py:156–177`.

Refresh проверяется только криптографически; состояние сессии, использованный `jti` и отзыв отсутствуют в этой цепочке. Выдача новой пары не делает прежний refresh недействительным. Смена пароля меняет только хеш пароля.

Подтверждение: один исходный refresh дважды подряд отправлен в `/api/auth/refresh`; оба ответа — 200.

Правка: таблица сессий с хешем refresh, сроком жизни и семейством токенов; атомарное погашение старого и выпуск нового. Повторное применение погашенного токена отзывает семейство. При смене пароля и выходе отзывать соответствующие сессии. Добавить параллельный тест двух запросов с одним refresh. Согласовать с Android TokenAuthenticator и будущим обновлением сессии портала.

### A04 · P1 · Деактивация организации не блокирует HTTP-сессию

Код: `server/app/services/auth.py:99–133`. Для сравнения: login, refresh и WebSocket проверяют активность организации.

`get_current_user` проверяет активность самого пользователя, но не его организации.

Подтверждение: после изменения `organization.is_active=False` старый access по-прежнему разрешался общей HTTP-зависимостью. `/api/auth/me` также вернул 200 с refresh как Bearer после отключения организации.

Правка: одна политика активности аккаунта и организации для всех транспортов. Добавить тест: войти → отключить организацию → проверить существующие access, refresh и WebSocket. Для уже открытого WebSocket отдельно определить механизм отзыва/повторной проверки, поскольку проверка при подключении не отзывает открытое соединение.

### A05 · P1 · SQLite-сессии разделяют одну транзакцию

Код: `server/app/models/base.py:48–64`, `create_db_engine`.

`StaticPool` применяется ко всем SQLite URL, включая файловую production-БД. Разные SQLAlchemy Session получают одно DBAPI-соединение, что опасно при пересечении запросов и фоновых операций.

Подтверждение на отдельном временном SQLite-файле: сессия A вставила строку без commit; B увидела её; `B.rollback()` отменил запись A; после `A.commit()` таблица осталась пустой. Дополнительно `PRAGMA foreign_keys` вернул 0.

Правка: выделить режим in-memory тестов; для файловой БД использовать отдельные соединения с обычным пулом. Настроить `foreign_keys=ON`, busy timeout и проверить целесообразность WAL. Перед включением FK проверить и устранить существующие сиротские записи. Для production с несколькими процессами рассмотреть уже поддерживаемый PostgreSQL. Добавить тест пересекающихся сессий на файловом SQLite.

Это поведение соответствует предупреждению [SQLAlchemy о StaticPool и общей транзакции](https://docs.sqlalchemy.org/en/20/dialects/sqlite.html).

### A06 · P1 · Запуск может скрывать неприменённые миграции

Код: `server/app/models/base.py:122–213`, `server/main.py:115–116`.

Есть две проблемы: исключение миграции логируется и поглощается; legacy-БД с `users.avatar_path` автоматически получает `stamp head` без проверки более поздних изменений. Последующий `create_all` не добавляет отсутствующие колонки к существующим таблицам.

Подтверждения:

- Искусственная ошибка Alembic не вышла из `run_migrations`: вызывающий код продолжает запуск.
- Отдельная временная legacy-БД с `users.avatar_path` получила ревизию `20260701_0001`, но после `run_migrations()` и `init_db()` в существующей `tasks` всё ещё не было `created_by_id`.

Правка: в production завершать запуск при ошибке схемы; выполнять миграции отдельным шагом релиза. Автоматическое угадывание legacy-ревизии заменить проверяемым разовым импортом/baseline. Добавить тесты upgrade с поддерживаемых старых схем на SQLite и PostgreSQL и отдельный тест чистой установки. Зафиксировать одно место запуска миграций при нескольких процессах.

### A07 · P1 · WebSocket-событие без organization_id уходит всем организациям

Код: `server/app/services/websocket_manager.py:142–179`, `broadcast_task_created:245–264`.

Фильтр tenant применяется только при `organization_id is not None`. Заявки без организации допустимы для суперадмина; их события содержат номер и заголовок. Значение None сейчас означает одновременно «legacy-данные без организации» и «общая рассылка».

Подтверждение: две тестовые WebSocket-сессии разных организаций получили событие с `organization_id=None`.

Правка: разделить явную глобальную системную рассылку и рассылку данных конкретного tenant, включая legacy None. Для задач без организации выбирать только разрешённых legacy-получателей и суперадминов. Добавить матрицу тестов org A / org B / legacy / superadmin.

### A08 · P1 · Офлайн-изменение плановой даты не отправляется на сервер

Код: `app/src/main/java/com/fieldworker/data/repository/OfflineFirstTasksRepository.kt:368–405`, `app/src/main/java/com/fieldworker/data/local/entity/PendingAction.kt:29–32`.

Офлайн-ветка меняет Room-запись и ставит `isLocallyModified=true`, но не создаёт pending action. В очереди реализованы только UPDATE_STATUS и ADD_COMMENT. `refreshTasks` затем сохраняет серверную версию через `upsertTasks`.

Последствие по цепочке кода: пользователь получает успешный результат локального изменения даты, но после восстановления сети изменение не отправляется и может быть затёрто серверным значением.

Правка: добавить UPDATE_PLANNED_DATE с корректной поддержкой null; менять локальную запись и очередь в одной Room-транзакции. При обновлении сохранять поля с незавершёнными локальными операциями. Тест: изменить дату без сети → перезапустить приложение → восстановить сеть → проверить сервер и локальный кеш. Вывод установлен по коду; инструментальный Android-сценарий не выполнялся.

### A09 · P1 · Небезопасный bootstrap разрешён в production

Код: `server/app/services/auth.py:234–258`, `server/app/config.py:280–296`, `server/main.py:118–122`.

Пустая БД автоматически получает известные admin/admin и user/user. Дефолтный JWT secret в production вызывает только предупреждение. Наличие этих значений в действующем окружении не проверялось; проблема в разрешённом поведении новой установки.

Правка: production-конфигурация с дефолтным ключом должна завершаться ошибкой; убрать создание демонстрационных аккаунтов из startup. Первого администратора создавать отдельной командой с заданным секретом, а demo seed оставить явной dev-командой. Добавить проверки опасных production-настроек.

### A10 · P2 · Пагинация допускает ошибочные и неограниченные размеры

Код: `server/app/api/tasks/core.py:119–121, 242–252`.

Подтверждение в тестовой БД: `size=0` → HTTP 500 с ZeroDivisionError; `size=-1` и `size=1000000` → 200. На SQLite отрицательный LIMIT снимает ограничение выдачи.

Правка: `page=Query(1, ge=1)`, `size=Query(20, ge=1, le=100)` либо согласованный максимум. Проверить аналогичные списки. Добавить граничные тесты. Отдельно не загружать все тексты комментариев только ради `comments_count`: текущие `subqueryload(TaskModel.comments)` и `len(task.comments)` заменить SQL-агрегацией. Профилировать запросы на реалистичном объёме.

### A11 · P2 · Блокирующая работа выполняется внутри async-обработчиков

Код: `server/app/api/auth/session.py:53–104`, `server/app/api/tasks/core.py:67–98`, `server/app/services/task_service.py:226`, `server/app/services/task_queue.py:131–135`.

Синхронные SQLAlchemy, bcrypt и геокодер вызываются непосредственно из async-функций. Постановка в ARQ может синхронно ждать до трёх секунд. Это блокирует event loop данного процесса и способно задержать другие HTTP-запросы и WebSocket.

Правка: переносить целые синхронные операции с собственной Session в threadpool или обычные def-обработчики; для смешанных async-потоков использовать явные границы. Полный переход на AsyncSession допустим как отдельная задача, но не обязателен для первого исправления. Геокодирование и тяжёлые экспорты вынести в фон при подходящем UX. Проверить конкурентную задержку login/create-task/WS, включая недоступный геокодер и Redis.

Правила исполнения обычных функций внутри async описаны в [документации FastAPI](https://fastapi.tiangolo.com/async/#other-utility-functions).

### A12 · P2 · Очередь Android не гарантирует единственного исполнителя и сохранность pending-данных

Код: `OfflineFirstTasksRepository.kt:101–139, 412–485`, `app/src/main/java/com/fieldworker/data/sync/SyncManager.kt:31–52`, `SyncWorker.kt:62–85`.

Немедленный и периодический WorkManager используют разные имена; синхронизацию также вызывает refreshTasks. В репозитории нет сериализации или атомарного захвата pending action. Два запуска способны прочитать одну очередь и повторно отправить комментарий. Серверная версия при refresh сохраняется поверх локальной даже после неудачной отправки. Ошибка обновления сети также может превращаться в Result.success(cache), после чего Worker сообщает об успехе.

Правка: один координатор синхронизации и Mutex/атомарный claim очереди; идентификатор операции с серверной идемпотентностью; последовательность операций по заявке; транзакционное изменение Room и outbox. Возвращать отдельный результат «данные доступны из кеша», «сервер синхронизирован», «есть ошибки/конфликт». CancellationException пробрасывать. Постоянные 4xx не повторять бесконечно, показывать пользователю конфликт. Проверить конкурентные sync, потерянный ответ сервера, отмену Worker и отказ 403/422.

### A13 · P2 · Healthcheck не сообщает HTTP-ошибку при недоступной БД

Код: `server/main.py:425–437`, `docker-compose.yml` и `server/Dockerfile` используют `curl -f /health`.

При исключении БД возвращается JSON `status=degraded` с обычным HTTP 200. Поэтому curl-healthcheck продолжает считать контейнер здоровым.

Правка: разделить liveness и readiness. Readiness при недоступной обязательной зависимости возвращает 503; проверка контейнера/балансировщика использует согласованный endpoint. Проверять не только SELECT 1, но и готовность ожидаемой схемы после миграции. Не публиковать подробный текст внутренних исключений наружу.

### A14 · P2 · Граница транзакции создания заявки раздроблена

Код: `server/app/services/task_service.py:383–390`, `server/app/api/tasks/core.py:94–98`.

Создание делает commit до генерации номера, второй commit после неё, затем контроллер делает ещё один. Сбой между этими шагами оставляет частично завершённую операцию, а повтор клиента способен создать ещё одну заявку.

Правка: один владелец транзакции на бизнес-операцию; `flush()` для получения id, затем формирование номера и единый commit. Уведомления и события — после commit, для гарантированной доставки через transactional outbox. Не добавлять универсальный Repository/UnitOfWork ради каждого простого запроса: сначала исправить конкретные границы.

## Улучшения архитектуры и сопровождения

1. **Сохранить модульный монолит.** Дальше разделять по предметным областям tasks/auth/chat/organizations, упрощая зависимости сервисов. Сейчас сервисы зависят от FastAPI Depends, а ряд правил и commit остаются в роутерах. Постепенно отделять бизнес-операцию от транспорта в затрагиваемых участках.
2. **Android: обратить зависимость domain → data.** В `domain/usecase/GetTasksUseCase.kt:4–17` импортируется конкретный OfflineFirstTasksRepository. Ввести интерфейс TasksRepository в domain, связать реализацию через Hilt. Отдельные Gradle-модули вводить после стабилизации границ, начиная с domain; много мелких модулей пока не требуется.
3. **Портал: завершить жизненный цикл сессии.** В `portal/src/api/client.ts:35–42` любой 401 удаляет сессию, а `authStore.ts` не сохраняет refresh. После серверной ротации добавить один общий refresh на параллельные 401 и однократный повтор запросов. В `authStore.ts:79` убрать trim пароля: пробелы являются частью пароля. Хранение refresh в HttpOnly-cookie потребует отдельного согласованного CSRF/cookie-дизайна.
4. **Денежные значения.** `TaskModel.payment_amount` хранится как Float. Перевести сумму в integer minor units либо Numeric/Decimal, с явными правилами округления и миграцией. Согласовать формат API и Kotlin-модель; проверить агрегаты и CSV/Excel.
5. **Запросы и индексы.** Измерить EXPLAIN и p95 на выборках tenant/status/assignee/planned_date; по результату добавить составные индексы с organization_id. Для больших карт/синхронизации рассмотреть изменения по cursor/updated_at с удалениями-tombstone, вместо полной выгрузки всех страниц. Для стабильной пагинации добавить id как tie-breaker сортировки.
6. **Realtime перед масштабированием.** ConnectionManager, rate limiter, membership-cache и scheduler имеют состояние процесса. Несколько API-процессов потребуют доставки событий через Redis Pub/Sub/Streams, общего лимитера и одного владельца scheduler. Не увеличивать workers до решения этих вопросов.
7. **Деплой.** Production Compose монтирует весь `./server:/app`, перекрывая содержимое образа. Перейти к собранному неизменяемому образу, отдельным томам данных/uploads/backups/logs и миграционному шагу. Добавить ограничения ресурсов и восстановление из резервной копии как проверяемый сценарий.
8. **Логи.** `main.py:112` выводит DATABASE_URL, `models/base.py:98–104` — его префикс. Для PostgreSQL это может включать пароль. Использовать маскирование URL; добавить request_id в реальные записи JSON-логов. Конкретные значения секретов не исследовались.
9. **CI.** В Portal CI выполняются tsc/build, но не существующие npm test и npm run lint. Для Android workflow отсутствует в текущем наборе: добавить JVM-тесты и compile/lint. Генерацию OpenAPI проверять на drift. Добавить startup/migration-тесты: текущая TestClient-фикстура без контекстного менеджера не выполняет lifespan, а схема тестов создаётся через create_all.
10. **Зависимости и тестовая конфигурация.** Зафиксировать Python test/dev зависимости, исключить влияние локального .env на тесты, явно задавать тестовые настройки. Runtime requirements фиксируют прямые версии, но транзитивное дерево остаётся плавающим. Ввести воспроизводимый lock и регулярную проверку advisories без бессистемного обновления всех библиотек.
11. **Покрытие важных сценариев.** Портал имеет 53 теста в пяти файлах утилит; отсутствует подтверждённое этими тестами покрытие пользовательских потоков. Добавить login/refresh, смену организации, realtime cache и создание/редактирование заявки. Для бота — тесты авторизации, повторной доставки и стабильной привязки разрешённых chat_id; названия групп изменяемы.
12. **Документация.** README указывает Android 2.34.3 против 2.36.0 в Gradle и coverage ≥50% против 75% в workflow. Обновлять метаданные из одного источника и описать точные команды проверок.
